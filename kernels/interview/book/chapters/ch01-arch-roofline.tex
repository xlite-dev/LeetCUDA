\chapter{GPU 架构、执行模型与 Roofline}\label{ch:01}

\section{本章导读}

这是全书的第一章。在动手写任何 kernel 之前，我们必须先回答一个更基本的问题：
\textbf{GPU 到底是怎么跑代码的，瓶颈到底藏在哪里？}这一章把 base.cuh 开头的
Phase 0「面试速查表」（L1--86）扩写成一篇完整的第一课：从 SM（Streaming
Multiprocessor，流式多处理器）的内部结构讲起，穿过 SIMT 执行模型与内存层级，
最终落到本章的主角——\textbf{Roofline 模型}：一个只靠乘除法就能预估 kernel
性能上限的思维工具。

本章不引入任何新的编译宏与架构限定（全 arch 通用），也没有 device kernel——
配合的最小测试 ch01\_roofline.cu 是一个 host 侧演示程序：对一组典型算子计算
算术强度并与解析期望值核对，同时打印本机 GPU 的资源与理论带宽。后续所有章节
的「性能分析」节都会反复使用本章建立的词汇表：算术强度（AI）、ridge point、
memory-bound 与 compute-bound、occupancy 与延迟隐藏。

\textbf{前置}：无。\textbf{源码区间}：base.cuh L1--86。\textbf{预计篇幅}：约 11 页。

\section{问题与动机}

先建立一个直觉：CPU 和 GPU 是两种设计哲学的产物。CPU 的目标是\textbf{尽快完成
一个任务}（低延迟），于是它把晶体管花在大容量 cache、复杂的分支预测与乱序执行
引擎上；GPU 的目标是\textbf{同时完成海量任务}（高吞吐），于是它把晶体管花在
成千上万个算术逻辑单元（ALU）上，寄存器文件巨大而 cache 相对很小，分支预测
几乎不存在——因为 GPU 根本不打算「预测」分支，它靠成千上万个线程之间的快速
切换把内存延迟藏起来。

这带来一个直接的后果：\textbf{同一个算法在 GPU 上快慢与否，几乎完全由它的
「访存-计算比例」决定}。一个向量加法（读两个数、加一次、写一个数）与一个
矩阵乘法（读两个数要做几十上百次乘加）在 CPU 上差异不大，在 GPU 上却是天壤
之别——前者把大部分时间花在等数据上（memory-bound），后者才能喂饱计算单元
（compute-bound）。base.cuh L22--26 把这种判断浓缩成了三行注释：

\lstinputlisting[linerange={22-30},firstnumber=auto,
  title={base.cuh L22-30（关键瓶颈判断与 occupancy 公式）}]{../base.cuh}

这三行注释就是本章的路线图。第一行与第二行给出判断标准——比较算术强度与
机器的「转折点」；第三行点出第三种容易被忽略的瓶颈：latency-bound，它甚至
与算法无关，纯粹是并行度不够、延迟藏不住的问题。要把这三行注释看懂，我们

\section{SM 内部结构与内存层级}\label{sec:ch01-sm}

\subsection{SM：GPU 的基本计算单元}

GPU 是由大量 SM 组成的阵列。以本章测试机 RTX PRO 5000（Blackwell，sm\_120）
为例，一块芯片上有 110 个 SM；每个 SM 内部的关键部件在 base.cuh L8--14 中
有一条速查清单：

\lstinputlisting[linerange={7-21},firstnumber=auto,
  title={base.cuh L7-21（SM 内部结构与内存层级速查）}]{../base.cuh}

逐条展开：

\begin{itemize}
\item \textbf{Warp Scheduler $\times$ 4}：每个 SM 有 4 个 warp scheduler，
  每个每周期可以发射 1 条指令。这意味着一个 SM 每周期最多发出 4 条指令，
  「发射带宽」本身就是一种资源。
\item \textbf{Register File}：每 SM $65536 \times 32$-bit $= 256$ KB。
  这是 GPU 上最宝贵也最快的存储：所有活跃线程的寄存器都从这里分配。寄存器
  分配以 warp 为粒度均分——若 kernel 每线程用 64 个寄存器，一个 256 线程的
  block 就要占 $256 \times 64 \times 4\,\mathrm{B} = 64$ KB，SM 里最多驻留
  4 个这样的 block。
\item \textbf{Shared Memory / L1}：同一块 256 KB 片上 SRAM 中可配置划分出
  的共享内存部分，Hopper 上最多约 228 KB/SM 可用作 smem（SM80 为 163 KB，
  SM120 本机实测 opt-in 上限为 99 KB，见 \S\ref{sec:ch01-test}）。它是
  block 内线程交换数据的主战场，也是后续章节 bank conflict（ch07）、
  swizzle（ch12）故事的舞台。
\item \textbf{Tensor Cores}：Hopper 每 SM 4 个第四代 Tensor Core，专门执行
  矩阵乘加（MMA）；Blackwell 的数量与形态随型号有差异，源码注释提醒「以
  官方 ISV guide 为准」是严谨的做法。本书 Part II--IV 的大量篇幅都在围绕
  如何喂饱这些 Tensor Core。
\item \textbf{Warp = 32 threads}：warp 是\textbf{最小调度与指令发射单元}，
  32 个线程锁步执行同一条指令（SIMT）。注意区分两个概念：线程是\textbf{执行}
  的最小粒度，warp 是\textbf{调度与发射}的最小粒度。硬件把 32 条「线程通道」
  捆绑成一个 warp，用一套取指-译码-发射逻辑服务 32 个计算 lane——这就是
  GPU 用少量控制逻辑驱动海量 ALU 的秘密。
\end{itemize}

\subsection{内存层级：一场带宽与容量的交易}

base.cuh L16--21 给出了 H100 参考下的带宽数量级：HBM3 约 3.35 TB/s（理论值，
实际约 2.5--3.0 TB/s）、L2 约 12 TB/s、L1/SMEM 约 19 TB/s、寄存器等效带宽
100+ TB/s。把这些数字画成金字塔（图 ch01-1），规律一目了然：\textbf{越靠近
计算单元，带宽越高、容量越小}，每一级之间的带宽差距都在 1.5--2 倍以上，而
容量差距是数十倍。

\centering
\includegraphics[width=0.95\textwidth]{figures/drawio/fig-1-1-mem-hierarchy/fig-1-1.png}
\caption{GPU 内存层级金字塔：离 SM 越远带宽越低、容量越大（H100 数量级，base.cuh L16--21 口径）。}

这张图解释了 GPU 编程的第一定律：\textbf{数据每向上爬一层，就快一个台阶；

TMA+Warp Specialization 把「搬运」与「计算」解耦成流水线——全部是这条定律
的具体化。

\section{数学原理：Roofline 与算术强度}\label{sec:ch01-math}

\subsection{算术强度（Arithmetic Intensity, AI）}

定义一个算法（或一段 kernel）的算术强度：
\begin{equation}
  AI \;=\; \frac{\mathrm{FLOPs}}{\mathrm{Bytes}},
  \label{eq:ch01-ai}
\end{equation}
其中 FLOPs 是算法需要的浮点运算次数（\textbf{总量}，单位 FLOP，不是每秒），
Bytes 是它必然要在\textbf{最外层存储}（通常是 HBM）上搬运的字节数，口径是
「每个数据读一次、写一次」。AI 的单位是 FLOP/Byte，物理含义是：\textbf{每
搬运 1 字节，能换来多少次浮点运算}。

三个注意点。第一，FLOPs 数「算法固有」的量：乘加各记 1 次，因此一个点积
$a\cdot b$（$N$ 项）是 $2N$ 次。第二，Bytes 是\textbf{不可再省的下界}：
若算法要读一遍 $a$ 写一遍 $y$，无论 cache 多聪明，HBM 流量都不会低于
$4(|a|+|y|)$ 字节（fp32）。第三，中间量不算：softmax 的逐元素 max、exp、
sum 都在寄存器里完成，不出 HBM，所以不计入 Bytes。

\subsection{三个典型算子的 AI 逐项推导}

\textbf{GEMM（$C = AB$，尺寸 $M{\times}K$ 乘 $K{\times}N$）。}输出 $C$ 有
$M \times N$ 个元素，每个元素 $c\sb{ij} = \sum\sb{k} a\sb{ik} b\sb{kj}$ 需要
$K$ 次乘与 $K$ 次加，共 $2K$ 次；所以
\begin{equation}
  \mathrm{FLOPs} = 2MNK .
\end{equation}
Bytes 按「三个矩阵各读写一次」计：
\begin{equation}
  \mathrm{Bytes} = 4\,(MK + KN + MN).
\end{equation}
当 $M = N = K$ 时有简洁的解析形式：
\begin{equation}
  AI\sb{\mathrm{GEMM}} = \frac{2K^3}{3K^2 \cdot 4} = \frac{K}{6},
  \label{eq:ch01-gemm-ai}
\end{equation}
$K = 4096$ 时 $AI = 682.7$ FLOP/Byte——这正是 base.cuh L75--79 注释中
「$\approx 685$」的来源（注释取了 $137\mathrm{G}/200\mathrm{M}$ 的粗略值，
精确值是 682.67，见 \S\ref{sec:ch01-kaogu}）。AI 随 $K$ \textbf{线性增长}：
GEMM 是天生的 compute-bound 算法，矩阵越大越「划算」，这也是它适合 GPU 与
Tensor Core 的根本原因。

\textbf{GEMV（$y = Ax$）。}$A$ 是 $M{\times}K$，$x$ 是 $K$ 维向量，$y$ 是
$M$ 维输出。$y$ 的每个元素要 $K$ 次乘 $K$ 次加，$\mathrm{FLOPs} = 2MK$；
而 $\mathrm{Bytes} = 4(MK + K + M)$。大 $MK$ 主导下：
\begin{equation}
  AI\sb{\mathrm{GEMV}} \approx \frac{2MK}{4MK} = 0.5 \ \mathrm{FLOP/Byte}.
\end{equation}
矩阵 $A$ 里的每个元素只用一次就被扔掉，没有任何复用——AI 被「读一次只用
一次」钉死在 0.5，比 GEMM 低三个数量级，是彻底的 memory-bound。ch08 将看到
三种 warp 划分方式如何逼近这 0.5 对应的理论带宽。

\textbf{Softmax（逐 token，宽度 $N$）。}对长度 $N$ 的行做 softmax：1 次 max
比较、$N$ 次减法与 exp（计 $2N$）、$N$ 次求和、$N$ 次除法，共约 $5N$
FLOPs；访存是读入 $x$、写出 $y$ 各一次，$4 \times 2N$ 字节：
\begin{equation}
  AI\sb{\mathrm{softmax}} = \frac{5N}{8N} = \frac{5}{8} = 0.625,
\end{equation}
与 base.cuh L85 的口径一致。ch04 的三级递进（naive $\to$ safe $\to$ online）
优化的是访存\textbf{趟数}（3-pass $\to$ 1-pass），而 AI 的上限 0.625 告诉
我们：无论怎么优化，它始终是 memory-bound，最终成绩用「离理论带宽多近」来
打分。

\subsection{Roofline 模型与 ridge point}

把机器的两个峰值——峰值算力 $P\sb{peak}$（FLOP/s）与峰值带宽 $BW$
（Byte/s）——放在一起，Roofline 模型给出任意算子的可达性能上界：
\begin{equation}
  P \;=\; \min\bigl(P\sb{peak},\; AI \times BW\bigr).
  \label{eq:ch01-roofline}
\end{equation}
它的图像（图 ch01-2）是一整条「屋顶线」：左边是一段斜率为 $BW$ 的斜坡
（每多 1 FLOP/Byte 的强度就多 $BW$ 的性能——带宽是瓶颈），右边是一段水平
的「天花板」（$P\sb{peak}$——算力是瓶颈）。两段交点的横坐标叫
\textbf{ridge point}：
\begin{equation}
  AI^{*} \;=\; \frac{P\sb{peak}}{BW}.
  \label{eq:ch01-ridge}
\end{equation}
判断规则由此而来：$AI < AI^{*}$ 则 memory-bound，$AI > AI^{*}$ 则
compute-bound。

\begin{figure}[htbp]
\centering
\includegraphics[width=0.95\textwidth]{figures/drawio/fig-1-2-roofline/fig-1-2.png}
\caption{Roofline 模型：$P = \min(P_{\mathrm{peak}}, \mathrm{AI} \times \mathrm{BW})$，脊点 $\mathrm{AI}^* = P_{\mathrm{peak}} / \mathrm{BW}$。GEMM $K{=}4096$（AI$=683$）落在计算屋顶，softmax（AI$=0.625$）落在带宽斜线区。}
\label{fig:1-2}
\end{figure}

\textbf{同一个 GPU 有多条屋顶线}。FP32 CUDA core 与 FP16 Tensor Core 的
$P\sb{peak}$ 相差约 15 倍，于是 ridge point 也相差 15 倍：在 H100 上，
AI=100 的算子用 FP32 跑是 compute-bound（$100 > 20$），切到 FP16 TC 反而是
memory-bound（$100 < 295$）。这解释了一个反直觉的现象：\textbf{把 kernel
迁移到 Tensor Core 上未必变快}——如果它本是 memory-bound，算力翻 15 倍也
无济于事。同理，把 ridge point 算错（比如把 sparse 峰值当 dense 用，见
\S\ref{sec:ch01-pitfall}）会把 bound 类别判反，整个优化方向就全错了。

\subsection{Occupancy 与延迟隐藏}

Roofline 描述「算法-机器」的匹配，occupancy 描述「实现」的并行度。
GPU 隐藏内存延迟靠的不是 cache（容量太小），而是\textbf{warp 切换}：当
warp A 因等 HBM 数据而停顿时，scheduler 立刻切到 warp B 发射指令；等到
A 的数据到了再切回来。设单次 HBM 访问约 $500 \sim 800$ 个时钟周期，若要
把发射口喂满，SM 上必须常驻足够多的活跃 warp。活跃 warp 数与硬件上限之比
就是 occupancy（base.cuh L27--30）：
\begin{equation}
  \mathrm{occupancy} = \frac{\text{active warps / SM}}
                            {\text{max warps / SM}},
\end{equation}
它同时受三类资源钳制，实际值取各约束下的最小值：每线程寄存器数（寄存器
用得越猛，能驻留的 warp 越少）、每 block 的 smem 用量（smem 用得多，
block 数就少）、block 大小（block 太小则凑不满 SM 的线程槽位）。本书后续
反复出现这类权衡：ch12 的寄存器双缓冲用更多寄存器换流水线，ch14 的
setmaxnreg 干脆在 producer/consumer 之间\textbf{动态重新分配}寄存器池——
都是在 occupancy 这杆秤上做加减法。

\section{实践经验}\label{sec:ch01-kaogu}

本章对 base.cuh L1--86 注释逐条核查（F1 架构事实/F3 数学/F4 性能断言），
以下两条值得读者留意，全量记录见 book/CHECKLOG.md：

\begin{kaogu}[F4]{L16--21 内存层级带宽数量级}
「L2 约 12 TB/s、L1/SMEM 约 19 TB/s」属于微基准口径的数量级估计，随测量
方法（读/写比例、跨 SM 通信模式）浮动明显；HBM 3.35 TB/s 则是 H100 SXM 的

避免读者按同一精度理解这组数字。
\end{kaogu}

\begin{kaogu}[F3]{L89 GEMM 算例单位}
注释「FLOPs $= 2 \times 4096^3 \approx 137$ GFLOPS」中单位应为
GFLOP（运算\textbf{量}），FLOPS（每秒）是速率单位；该段实为 Roofline 的
静态算例，与时间无关。精确值 $2 \times 4096^3 / (3 \times 4096^2 \times 4)
= 682.7$ FLOP/Byte，注释的 685 为四舍五入口径。
\end{kaogu}

\section{常见坑}\label{sec:ch01-pitfall}

\begin{enumerate}
\item \textbf{Bytes 漏算写回}。AI 分母必须包含输出写回（读 $a,b$ 写 $y$
  是 $3 \times 4N$ 字节，不是 $2 \times 4N$）；漏算会把 memory-bound 算成
  compute-bound。
\item \textbf{sparse 峰值当 dense 用}。NVIDIA 规格表上带 sparsity 的
  TFLOPS 是稠密口径的两倍；ridge point 差一倍，bound 类别可能判反
  （H100 FP16 TC：1979 sparse vs 989 dense，对应 $AI^{*}$ 590 vs 295）。
\item \textbf{把 occupancy 当唯一 KPI}。occupancy 上限 100\% 需要「少用
  寄存器/少用 smem」，但 GEMM 类 kernel 恰恰要用大 thread tile 与多级
  smem 流水换性能；低 occupancy + 高 ILP 常优于高 occupancy + 低 ILP。
  occupancy 是手段，roofline 位置才是目标。
\item \textbf{用小数据集标定带宽}。16 MB 的输入永远命中 96 MB 的 L2，
  测出的「带宽」是 L2 的（ch03 实测 1862 GB/s $>$ HBM 理论 1344 GB/s）。
  标定 HBM 带宽时数据集至少要数倍于 L2 容量。
\item \textbf{混淆 FLOP 与 FLOPS}。AI 的分子是运算量（FLOP），roofline
  纵轴是速率（FLOP/s）；单位写错，量纲就全乱了（参见
  \S\ref{sec:ch01-kaogu} 第二条）。
\end{enumerate}

\section{面试要点速查}

\begin{itemize}
\item \textbf{Q：warp 是什么？为什么是 32？}\\
  A：最小调度与指令发射单元，32 线程锁步（SIMT）。32 与 warp scheduler 的
  每周期发射粒度、寄存器文件 bank 宽度匹配；发散（divergence）会让一个
  warp 内的分支两条路径串行执行，等效指令数翻倍。
\item \textbf{Q：一句话说清 memory-bound 与 compute-bound？}\\
  A：算 AI，与 ridge point $AI^{*} = P\sb{peak}/BW$ 比较：低于则带宽瓶颈，
  高于则算力瓶颈。优化方向完全不同：前者想 coalescing/向量化/tiling，
  后者想 Tensor Core/指令效率。
\item \textbf{Q：为什么需要 occupancy？}\\
  A：延迟隐藏。GPU 不做分支预测与深级乱序，靠大量活跃 warp 之间的快速切换
  填满发射口；occupancy 低则切换不了，HBM 延迟（约 500--800 cycle）直接
  暴露。但 occupancy 受寄存器/smem/block 大小三重钳制，是权衡不是越大越好。
\item \textbf{Q：寄存器溢出（spill）是什么？}\\
  A：每线程寄存器需求超过分配上限时，编译器把局部变量挪到 local memory
  （实际在 HBM/L1），访存量暴涨、延迟暴露。用
  \texttt{-{}-ptxas-options=-v} 观察 spill 次数，出现即优先 reconsider
  thread tile 大小。
\item \textbf{Q：L1 与 shared memory 的关系？}\\
  A：同一块片上 SRAM 的两种角色，可配置划分。L1 对所有访存透明缓存；
  smem 由程序员显式管理、block 内共享。Hopper 起 smem 上限约 228 KB/SM。
\end{itemize}

\section{最小测试与动手实验}\label{sec:ch01-test}

测试文件：book/tests/ch01\_roofline.cu（host 侧演示，无 GPU kernel）。
它做两件事：(1) 对 GEMM/GEMV/softmax/eadd/relu/dot 六个算子，按
\S\ref{sec:ch01-math} 的口径计算 FLOPs、Bytes 与 AI，并与解析期望常数
（682.67、0.5、0.625、1/12、1/8、0.25）核对；(2) 打印本机 GPU 的 SM 数、
L2、smem 上限、GDDR7 理论带宽与 FP32 峰值估算，作为全书 bench 的标尺来源。

编译与运行（CWD：book/tests/）：\texttt{./build\_tests.sh -{}-ch ch01}。

实测输出（RTX PRO 5000，sm\_120a，2026-09-11；末行设备名照录自驱动返回，
含架构代号 sm120）：
\begin{lstlisting}[style=console]
  PASS GEMM     FLOPs=1.3744e+11 Bytes=2.0133e+08 AI= 682.6667
  PASS GEMV     FLOPs=3.3554e+07 Bytes=6.7142e+07 AI=   0.4998
  PASS softmax  FLOPs=2.0480e+04 Bytes=3.2768e+04 AI=   0.6250
  PASS eadd     FLOPs=4.0960e+03 Bytes=4.9152e+04 AI=   0.0833
  PASS relu     FLOPs=4.0960e+03 Bytes=3.2768e+04 AI=   0.1250
  PASS dot      FLOPs=8.1920e+03 Bytes=3.2768e+04 AI=   0.2500
  name=NVIDIA RTX PRO 5000 72GB Blackwell sm120 SMs=110
  mem-theoretical-BW ~ 1344 GB/s   fp32-peak ~ 66.9 TFLOPS
  ridge-point ~ 49.8 FLOP/Byte
\end{lstlisting}

\textbf{动手实验}：把 softmax 的 FLOPs 口径从 $5N$ 改成 $3N$（不含减法与
除法的近似），观察 AI 变为 0.375——结论不变（仍然 memory-bound），这说明
roofline 对 FLOPs 计数的容错性很高：AI 相差一倍通常不会翻转 bound 类别，
但把分母的 Bytes 算漏一项就可能翻转。
